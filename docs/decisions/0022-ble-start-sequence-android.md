# ADR 0022: BLE Android Start Sequence Corrections

Status: Accepted
Date: 2026-05-10
Patches: [ADR 0016](0016-android-foreground-service.md), [ADR 0018](0018-ble-peripheral-advertising-android.md), [ADR 0020](0020-haptic-proximity-loop.md)

## Context

Review of the implemented `app/src/services/ble/index.android.ts` found four bugs that will cause the M1 lab test to fail silently or throw at runtime. Additionally, one bug was found in `app/src/hooks/useProximityHaptics.ts` (fires on descending band transitions contrary to ADR 0020) and one in `app/src/screens/Radar/index.tsx` (async start not awaited). None of these require new architectural decisions — they are implementation errors against existing accepted ADRs. This ADR documents the correct patterns so the engineer has an unambiguous target.

### Bug inventory

| # | File | Bug | Symptom |
|---|---|---|---|
| 1 | `ble/index.android.ts` | Malformed SERVICE_UUID (6-4-4-4-12 chars) | OS rejects UUID; scan finds nothing, advertise silently fails |
| 2 | `ble/index.android.ts` | `manager.startForegroundService()` called with no arguments | Foreground service never starts; app killed in background |
| 3 | `screens/Radar/index.tsx` | `bleService.start()` not awaited | Scan subscription race condition; first RSSI readings lost |
| 4 | `hooks/useProximityHaptics.ts` | Fires haptics on descending band transitions | User feels buzz when someone walks away (violates ADR 0020) |
| 5 | `services/api/index.ts` | Default base URL targets port 4000; backend runs on 3000 | All API calls fail when `EXPO_PUBLIC_API_BASE_URL` is unset |
| 6 | `services/bootstrap.ts` | `/api/config` never fetched | `BUZZ_COOLDOWN` never read from server; ADR 0012 config plumbing unproven |

## Decision

### Fix 1 — Correct SERVICE_UUID

Both `index.android.ts` and `index.ios.ts` must use a valid UUID v4 format (8-4-4-4-12 hex chars). Replace the malformed value:

```ts
// Wrong — 6 chars in first group
const SERVICE_UUID = 'f7a5c2-9d4e-11ef-b864-0242ac120002';

// Correct — generate once and pin it
const SERVICE_UUID = 'f7a5c2d9-9d4e-11ef-b864-0242ac120002';
```

This UUID is the same value with the missing two hex digits (`d9`) restored in the first group. Pin this value in both files — it is the app's BLE service identifier and must never change without a protocol migration.

### Fix 2 — Foreground service start with correct signature

`react-native-ble-plx` exposes `BleManager.startForegroundService(drawableIconName, title, message)` on Android (all three arguments required). The current implementation passes no arguments. Correct form:

```ts
// In index.android.ts, inside start():
try {
  this.manager.startForegroundService(
    'ic_notification',      // drawable resource name in the Android project
    'Alon is active',   // notification title
    'detecting nearby vibes', // notification body
  );
} catch (_) {
  // Foreground service unavailable (emulator, old API). Acceptable in dev.
}
```

The drawable `ic_notification` is the default small icon generated by the Expo managed build. No native file needs to be created — the Expo build provides it.

`manager.enable()` (line 34 of the current implementation) is correct Android-only API and stays as-is. It opens the system dialog to enable Bluetooth if it is off. Keep the call; it is not a bug.

### Fix 3 — Await `bleService.start()` in RadarScreen

`bleService.start()` is `async`. Calling it without `await` means `proximityService.start()` subscribes to RSSI readings before the scan subscription is attached. Change in `app/src/screens/Radar/index.tsx`:

```ts
// Inside the useEffect, replace:
bleService.start();
proximityService.start(bleService.onRssiReading.bind(bleService));

// With:
bleService.start().then(() => {
  proximityService.start(bleService.onRssiReading.bind(bleService));
});
```

Do not make the `useEffect` callback `async` — React will warn if an effect returns a Promise. Use `.then()` chaining instead.

The cleanup function is already correct and does not need to change.

### Fix 4 — Ascending-only haptic enforcement in `useProximityHaptics`

ADR 0020 states: *"Descending transitions (moving away) do not fire — silence is the correct signal for someone leaving range."* The current implementation fires for any band change except `out-of-range`, including `very-near → near` and `near → far`.

Add a direction check in `app/src/hooks/useProximityHaptics.ts`. The band priority order (ascending = moving closer) is:

```
out-of-range (0) < far (1) < near (2) < very-near (3)
```

```ts
const BAND_RANK: Record<ProximityBand, number> = {
  'out-of-range': 0,
  far: 1,
  near: 2,
  'very-near': 3,
};

// Inside the onBandChange callback, after the out-of-range guard:
const prevRank = BAND_RANK[lastFiredBand.current ?? 'out-of-range'];
const nextRank = BAND_RANK[band];
const isAscending = nextRank > prevRank;

if (!isAscending) return; // descending: silence is the signal
```

Place this check after the `out-of-range` guard and before the cooldown check. The `lastFiredBand` ref already tracks the previous band — use it for the rank comparison.

### Fix 5 — Correct default API port

`app/src/services/api/index.ts` line 4:

```ts
// Wrong
const BASE_URL = process.env.EXPO_PUBLIC_API_BASE_URL ?? 'http://localhost:4000/api';

// Correct
const BASE_URL = process.env.EXPO_PUBLIC_API_BASE_URL ?? 'http://localhost:3000/api';
```

Backend runs on port 3000 per ADR 0015. The fallback must match.

### Fix 6 — Fetch `/api/config` on bootstrap

ADR 0015 defines `GET /api/config → { BUZZ_COOLDOWN: number }`. ADR 0012 requires this endpoint to prove the platform config system works in M1.

Add to `app/src/services/api/index.ts`:

```ts
async fetchConfig(): Promise<{ BUZZ_COOLDOWN: number }> {
  const res = await fetch(`${BASE_URL}/config`);
  return (await checked(res)).json();
},
```

Add to `app/src/services/bootstrap.ts`, after the initial `registerDevice` call succeeds:

```ts
try {
  const config = await apiService.fetchConfig();
  // Store for future use — for M1, log it to confirm the endpoint works
  console.log('[bootstrap] BUZZ_COOLDOWN from server:', config.BUZZ_COOLDOWN);
} catch (err) {
  console.warn('[bootstrap] fetchConfig failed', err);
}
```

`BUZZ_COOLDOWN` is enforced server-side via Redis TTL (ADR 0015). The client does not need to hold it as state in M1 — logging it confirms the plumbing works. M2 will use it to inform UI (disable Buzz Me button when rate-limited).

## Alternatives considered

**Write a native Android module for the foreground service** — unnecessary; react-native-ble-plx's built-in `startForegroundService()` handles this for M1's controlled hardware target. Rejected.

**Make `useEffect` callback async to await `bleService.start()`** — React emits a warning when an effect callback returns a Promise. `.then()` chaining achieves the same result without the warning. Rejected.

**Silently ignore descending haptics (keep current implementation)** — The cooldown of 8 seconds partially masks it, but in a scenario where a user walks from `very-near` to `near` and pauses for 9 seconds, they'd feel a `steady_rhythm` buzz while the person is walking away. The spec is explicit: silence is the correct signal. Rejected.

**Block UI until `/api/config` resolves** — Adds latency to bootstrap with no user-visible benefit in M1. The server enforces the cooldown regardless. Rejected.

## Consequences

- `SERVICE_UUID` is now pinned to `f7a5c2d9-9d4e-11ef-b864-0242ac120002`. This value must stay identical across all devices in the M1 lab test — both devices must advertise and scan for the same UUID or they will not see each other.
- The foreground service notification will appear on-device during the M1 lab test. This is expected and required, not a bug.
- `useProximityHaptics` now only fires on closer-band transitions. The `BAND_RANK` lookup table is the single source of truth for band ordering — if new bands are added post-M1, update it there.
- Fix 6 adds one network call to bootstrap. On a cold start with no network, it will fail and log a warning — acceptable per the existing graceful degradation pattern.
- None of these fixes require new packages. All changes are in existing files.
